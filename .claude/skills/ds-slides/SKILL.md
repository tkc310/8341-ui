# デザインシステムに沿ってスライドを作る

スライドの見た目（文字サイズ・色・余白・揃え）は `scripts/slides/deck.css` が 8341-ui の semantic トークンだけで決める。作者が決めるのは **構成・文言・レイアウトの選択** だけにする。ルールの正は `docs/rulebook/07-slides.md`（S1〜S20）で、その元は `docs/design-principles/principles.md` と WCAG 2.2 である。

## 手順

各段階の文書は、その段階に入ったときに読む。最初からすべてを読まない。

1. **前提を聞く**: 推測できない項目だけを、短いリストで一度に聞く（Claude Code では AskUserQuestion、ほかでは番号付きの質問リスト）。目的（聞き手に何を決めて・知ってもらいたいか）、聞き手と前提知識、場（発表時間。1 分 1 枚が目安、投影か配布か、会場が暗いか）、使ってよい材料。答えを 3〜5 行で要約して確認する
2. **構成を決める（書く前に）**
   - 結論の 1 文を決め、表紙の次に `statement` で置く（S7）
   - 各スライドの見出し（`h2`）だけを並べた骨子を作る。見出しはそのスライドの結論を文で書く（S1）。見出しだけを順に読んで話が通じれば構成は良い
   - 章が 3 つ以上なら `section` で区切り、最後は `summary` で持ち帰ってほしいことを 3 つまで
   - 枚数が多い、または聞き手が重要なら、骨子をユーザーに見せて合意してから書く
3. **レイアウトを選んでソースを書く**: [authoring.md](./authoring.md) を読む。レイアウトの選び方・ソースの形・決まり・グラフの描き方がある。細部に迷ったら `docs/rulebook/07-slides.md` の該当する表だけを読む
4. **検査してビルドする**: `make slides-check SRC=<ソース>` → `make slides SRC=<ソース>`。エラーは必ず直す。警告（分量・強調の数・表の大きさ）は、理由が無ければ直す
5. **見た目を確かめて渡す**: [verify.md](./verify.md) を読む（ブラウザでの確認、セルフチェック、渡し方）

## やってはいけないこと

- ルールを緩めて検査を通す。ルールが合わない場面を見つけたら、作業を止めずに `docs/rulebook/07-slides.md` の改善案としてユーザーに伝える
- ソースに `style` 属性・`<style>`・`<script>`・独自のクラスを書く（S9）

## 直すとき

デッキの見た目・操作・検査を変えるのはデザインシステムの変更になる。`ds-improve` の手順で、`scripts/slides/`（`deck.css`・`deck.js`・`lib.ts`）と `docs/rulebook/07-slides.md` を同時に直す。使えるクラスやレイアウトを足すときは、`lib.ts` の `ALLOWED_CLASSES` / `LAYOUTS`、`deck.css`、07 章の表、見本（`scripts/slides/examples/sample.html`）をそろえる。`deck.css` には `var(--8341-*)` と `--deck-*` だけを書く。
