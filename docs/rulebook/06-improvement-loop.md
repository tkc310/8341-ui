# 06 改善ループ

このデザインシステムは「使う → 気づく → 記録する → 直す → 再発を防ぐ」を回して育てます。
人が回しても、AI エージェントが回しても同じ手順になるよう、各段階を仕組みにしています。

```
   ┌──────────── 使う（プロジェクトで利用）
   │                    │ 気づく
   │                    ▼
   │   ┌─ 自動: CI / 週次監査 ─┐   ┌─ 手動: Issue テンプレート ─┐
   │   └──────────┬──────────┘   └──────────┬──────────────┘
   │              ▼                          ▼
   │       docs/improvement/backlog.md（改善候補）
   │                    │ 直す（PR）
   │                    ▼
   │   ルール化: チェックスクリプト / テスト / ルールブック / ADR
   │                    │
   └──── docs/improvement/log.md に記録 ◀┘
```

## 1. 気づく

### 自動

| 仕組み                  | タイミング | 何を見つけるか                                                                                                                                                                    |
| ----------------------- | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `make check`（CI）      | PR ごと    | fmt・lint（oxlint、型情報つき）・型、コントラスト不足、テーマ間のキーずれ、生成物のずれ、クラス監査、アーキテクチャ違反（dependency-cruiser）、スライドとスキルの規約違反 |
| `make test`（Vitest 5） | PR ごと    | 振る舞いの退行（happy-dom）、全ストーリーの play 関数と axe による WCAG 違反（実ブラウザ）                                                                                        |
| VRT・e2e                | 手動・都度 | 見た目の退行（`make test-vrt`）、320px・200%・強制カラーでの崩れ（`make test-e2e`）                                                                                               |
| 週次監査ワークフロー    | 毎週月曜   | warning の蓄積、コントラストの余裕が 5% 未満の組み合わせ、未使用トークン、ストーリー・Code Connect の欠け。結果を Issue に起票                                                    |

### 手動

利用中に気づいたことは、GitHub の Issue テンプレート「改善提案」で起票します。
起票時に **どの原則・ルールに関係するか** を選ぶ欄があり、ルールブックのどこを直すべきかが分かるようにしています。

## 2. 記録する

改善候補は `docs/improvement/backlog.md` にまとめます（Issue と相互リンク）。
優先度は次の順で判断します。

1. アクセシビリティの不具合（誰かが使えない）
2. 一貫性の破れ（同じものが違って見える）
3. 開発体験（使いにくい API、足りない部品）
4. 見た目の好み

## 3. 直す

- 修正は PR で行い、PR テンプレートのチェックリスト（完了の定義）を満たす
- 見た目を変えたら、ローカルで `make storybook-preview` を実行して PR ごとの Storybook を GitHub Pages に公開し、変わったストーリーへのリンクを PR に添える（`.claude/skills/ds-storybook-preview/SKILL.md`）
- 値や方針を変えたら ADR を追加する（`docs/decisions/NNNN-*.md`）
- トークンを変えたら `make generate` で生成物を更新する（CI がずれを検出する）

## 4. 再発を防ぐ（いちばん大事）

**直しただけで終わらせない。** 同じ種類の問題が二度と起きないよう、次のどれかを必ず追加します。

| 問題の種類                       | 追加するもの                                                 |
| -------------------------------- | ------------------------------------------------------------ |
| 色の組み合わせのコントラスト不足 | `packages/tokens/src/contrast.rules.json` に組み合わせを追加 |
| クラスの書き方の問題             | `packages/ui/scripts/audit-classes.ts` にルールを追加        |
| 依存の向きの問題                 | `.dependency-cruiser.cjs` にルールを追加                     |
| lint で見つけられる問題          | ルートの `vite.config.ts` の `lint` ブロックにルールを追加   |
| 振る舞いの不具合                 | テストまたはストーリーの play 関数                           |
| 判断基準のあいまいさ             | ルールブックに追記                                           |

## 5. 振り返る

`docs/improvement/log.md` に 1 改善 1 行で記録します。
四半期ごとにログを見返し、同じ種類の改善が続いていればルールブックの章立てや原則そのものを見直します。

## AI エージェントが回す場合

手順は `ds-improve` スキル（`.claude/skills/ds-improve/SKILL.md`）。この章の 1〜5 を、エージェントが 1 件ずつ回す形にしたもの。
