# 前提条件のヒアリング

design-principles スキルを実行する際、最初に前提条件をユーザーとヒアリングする。すべての作業モード（新規作成、既存の調整、評価・レビュー）で、アウトプットを作る前に次の項目を確認する。

## ヒアリング項目

### 既存の情報の確認

リポジトリ内で確認できる情報を先に調べる：

- 既存の DESIGN.md の有無と内容
- コードベースから推測できるサービス種別（管理画面、社内向けツール、SaaS、toC）
- 既存のトークンやコンポーネント定義
- プロジェクトのドメイン（業務領域）
- 対象デバイス（コードやレスポンシブ設定から推測）

### ユーザーへの質問項目

リポジトリから推測できない項目のみを質問する。短いリストにまとめる。

#### 1. サービスとユーザー

- **サービス種別**: 管理画面、社内向けツール、SaaS、toC のいずれか（既存コードから推測できない場合のみ）
- **対象ユーザー**: 誰が使うか（職種、習熟度、利用頻度）
- **ドメインの専門性**: 専門的な業務領域か、日常的な対象か

#### 2. UI の方向性

- **オブジェクト指向 UI かタスク指向 UI か**: 既に決まっているか、判断が必要か
- **方向性の理由**: ドメインと対象ユーザーから判断した根拠

#### 3. 既存の制約

- **既存のデザインシステム**: 使用中のデザインシステムの有無（社内システム、外部ライブラリ）
- **ブランド制約**: ロゴ、配色、フォントなどの既定の要件
- **技術スタック**: フレームワークやライブラリの制約（既存コードから推測できない場合のみ）

#### 4. アクセシビリティ目標

- **達成基準のレベル**: WCAG 2.2 の Level A、AA、AAA のいずれを目標とするか（デフォルトは AA）
- **追加の要件**: 特定の支援技術への対応、業界基準など

#### 5. 作業の範囲

- **新規作成の場合**: どの画面から作るか、優先度
- **調整の場合**: どの部分を調整するか、理由
- **レビューの場合**: レビューの範囲（全体か特定の画面か）、懸念している点

#### 6. 求めるアウトプット

- **成果物の形式**: DESIGN.md、トークン定義、コンポーネント仕様、レビューレポートなど
- **詳細度**: 概要レベルか、実装可能な詳細レベルか
- **優先順位**: 最も重視する項目（アクセシビリティ、一貫性、実装速度など）

## ヒアリングの進め方

### 質問の構成

1. **既存情報の要約**: リポジトリから推測できた内容を示す
2. **確認が必要な項目**: 推測できない項目だけを質問する
3. **回答の確認**: ユーザーの回答を要約し、理解が正しいか確認する

### 質問の例

```
リポジトリを確認したところ、Next.js で実装された SaaS アプリケーションと推測しました。
既存の DESIGN.md は見つかりませんでした。

次の点を確認させてください：

1. 対象ユーザー: どのような方が使うサービスか（職種、習熟度）
2. UI の方向性: プロジェクト管理やドキュメント管理のように、対象（名詞）を中心に組み立てるオブジェクト指向 UI を想定していますか。それとも、申請や設定のように、作業（動詞）を中心に組み立てるタスク指向 UI を想定していますか。
3. 今回の作業範囲: 全画面の DESIGN.md を作成するか、特定の画面から始めるか

既存のブランド制約や技術的な制約があれば、教えてください。
```

## 回答の記録

ヒアリングで得た情報は、DESIGN.md の冒頭に記録する：

```markdown
# DESIGN.md

## プロダクト概要

- サービス種別: SaaS
- 対象ユーザー: 中小企業の経理担当者（月次決算業務に利用、会計知識あり）
- ドメイン: 会計・財務（専門的）
- UI の方向性: オブジェクト指向 UI（仕訳、勘定科目、取引先などの対象を中心に組み立てる）
- アクセシビリティ目標: WCAG 2.2 Level AA

## 対象デバイス

- デスクトップ（主要）
- タブレット（補助）

## 既存の制約

- ブランドカラー: #0066CC（プライマリ）、#FF6B00（アクセント）
- フォント: Noto Sans JP
- 技術スタック: Next.js 14、Tailwind CSS

...
```

## 注意事項

- ヒアリングは最小限にとどめる。リポジトリから推測できることは質問しない
- 質問は一度にまとめて行う。後から追加で聞くことは避ける
- ユーザーの回答を要約し、理解が正しいか確認してから作業を進める
- 前提条件が変わった場合は、DESIGN.md を更新する
