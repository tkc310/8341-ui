# デザイン段階で決める WCAG 2.2 の達成基準

この文書は、WCAG 2.2 の Level A と AA の達成基準のうち、画面のデザインで決まるものを、デザインシステムと DESIGN.md へ移せる形で並べる。基準は W3C 勧告（2024年12月12日版）の [WCAG 2.2](https://www.w3.org/TR/WCAG22/) に従う。改訂の有無は [W3C のクイックリファレンス](https://www.w3.org/WAI/WCAG22/quickref/) で確認する。

デザインで決まる、とは、配色、文字、レイアウト、部品の振る舞い、文言、画面の流れを決めた時点で、適合するかどうかがほぼ決まるという意味である。実装の書き方だけで決まる基準は、末尾に名前だけを置く。

## 強さの意味

各基準の「必須」は、達成基準の本文が要求する内容だけを書く。デザインシステムや DESIGN.md で外すことはできない。[サービス別の特化ルール](./services/README.md) と [ウェブデザインの原則](./principles.md) からも緩めない。

「推奨」は、基準より厳しいデザイン上の選択である。プロダクトごとに採るかどうかを決めてよい。特化ルールや原則が推奨と同じ内容を必須にしているときは、そちらの強さに従う。

## 知覚可能

### 1.1.1 非テキストコンテンツ（Level A）

[Understanding 1.1.1](https://www.w3.org/WAI/WCAG22/Understanding/non-text-content.html)

**意図**: 画像やアイコンが伝える内容を、見えない利用者にも同じ目的で渡す。

**必須**

- 情報を伝える画像、アイコン、図には、同じ目的を果たす代替テキストを用意する。
- 操作部品と入力欄が画像だけでできているときは、目的を表す名前を用意する。
- 純粋な装飾は、支援技術が読み飛ばせるものとして指定する。

**推奨**

- デザインの仕様に、画像ごとに「伝える内容」か「装飾」かを書く。
- 複雑なグラフは、本文か表で同じ内容を読めるようにする。

**レビュー**

- [ ] 情報を伝える画像に、代替テキストの内容が決まっているか
- [ ] アイコンだけのボタンに、名前が決まっているか
- [ ] 装飾の画像が、装飾として指定されているか

**トークン**: アイコン部品の契約で、名前を必須の属性にする。

### 1.3.1 情報及び関係性（Level A）

[Understanding 1.3.1](https://www.w3.org/WAI/WCAG22/Understanding/info-and-relationships.html)

**意図**: 見た目で表した構造（見出し、一覧、表、ラベルと入力欄の対応）を、見た目以外でも取り出せるようにする。

**必須**

- 見た目で見出しに見えるものは、見出しの段（大見出し、中見出し、小見出し）として仕様に書く。
- 一覧、表の行見出しと列見出し、ラベルと入力欄の対応を、仕様の上で明示する。

**レビュー**

- [ ] 見出しの段が、見た目の大小と一致しているか
- [ ] 表の見出しセルが決まっているか
- [ ] 各入力欄に対応するラベルが一つに決まっているか

**トークン**: 見出しの段ごとの文字スタイル。表の見出しセルのスタイル。

### 1.3.2 意味のある順序（Level A）

[Understanding 1.3.2](https://www.w3.org/WAI/WCAG22/Understanding/meaningful-sequence.html)

**意図**: 読む順で意味が変わる内容を、正しい順で読み上げられるようにする。

**必須**

- 順序が意味に関わる内容（手順、段組みの本文、ラベルと値）について、読む順を仕様に書く。

**推奨**

- 視覚上の並びと、読む順を一致させる。

**レビュー**

- [ ] 段組みやカードの並びで、読む順が決まっているか

### 1.3.3 感覚的な特徴（Level A）

[Understanding 1.3.3](https://www.w3.org/WAI/WCAG22/Understanding/sensory-characteristics.html)

**意図**: 形、色、大きさ、位置、向き、音だけに頼った指示を避ける。

**必須**

- 操作の説明が、形、色、大きさ、位置、向き、音のどれか一つだけで対象を指さないようにする。「右の丸いボタン」は、ボタンのラベルを添えて「右の『保存』ボタン」とする。

**レビュー**

- [ ] 説明文が、見た目の特徴だけで対象を指していないか

### 1.3.4 表示の向き（Level AA）

[Understanding 1.3.4](https://www.w3.org/WAI/WCAG22/Understanding/orientation.html)

**意図**: 端末を縦にも横にも置ける利用者が、どちらでも使えるようにする。

**必須**

- 画面を縦向きだけ、横向きだけに固定しない。向きが本質的に必要な場合（小切手の撮影、ピアノの鍵盤など）は除く。

**レビュー**

- [ ] 縦向きと横向きの両方のレイアウトがあるか

### 1.4.1 色の使用（Level A）

[Understanding 1.4.1](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)

**意図**: 色を見分けにくい利用者にも、情報、操作、状態が伝わるようにする。

**必須**

- 情報を伝える、操作を示す、応答を促す、要素を区別する、のいずれも、色だけを唯一の視覚的手段にしない。
- エラー、選択中、グラフの系列は、色に加えて、文字、アイコン、形、パターンのいずれかでも示す。

**推奨**

- 本文中のリンクには下線を付ける。下線を付けない場合、色だけで区別することになるため、周囲の文字とのコントラスト比 3:1 以上に加えて、ホバー時とフォーカス時に下線などの別の手がかりを出す。

**レビュー**

- [ ] グレースケールにしても、状態と系列が区別できるか
- [ ] 本文中のリンクが、色以外の手がかりでも分かるか

**トークン**: 状態ごとの色とアイコンを組で登録する。

### 1.4.2 音声の制御（Level A）

[Understanding 1.4.2](https://www.w3.org/WAI/WCAG22/Understanding/audio-control.html)

**意図**: 自動で鳴る音が、画面の読み上げを妨げないようにする。

**必須**

- 3 秒を超えて自動で流れる音には、止める手段か、システム全体とは別に音量を変える手段を置く。

**推奨**

- 音は自動で流さない。

**レビュー**

- [ ] 自動で流れる音に、停止か音量の操作があるか

### 1.4.3 コントラスト（最低限）（Level AA）

[Understanding 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

**意図**: コントラストの感度が下がった利用者にも、文字が読めるようにする。

**必須**

- 文字と文字画像の、背景とのコントラスト比を 4.5:1 以上にする。
- 大きい文字（18 ポイント以上、または太字で 14 ポイント以上。CSS ピクセルではおおよそ 24 と 18.5。日本語は同等の大きさ）は 3:1 以上でよい。
- プレースホルダー、ホバー時とフォーカス時に出る文字も対象に含める。
- 比は四捨五入しない。4.499:1 は 4.5:1 を満たさない。

**例外**

- 非アクティブな操作部品の文字、純粋な装飾、誰にも見えない文字、ほかに重要な視覚内容を含む写真の一部である文字。
- ロゴやブランド名の一部である文字。ブランドの規定を理由に、ロゴ以外の文字を例外にすることはできない。

**レビュー**

- [ ] 文字色と背景色の組を、すべて測ったか
- [ ] プレースホルダーと、ホバー時の文字を測ったか

**トークン**: 背景色と文字色を組で登録し、組ごとに比を記録する。大きい文字の組だけに使ってよい色は、用途を限って登録する。ライトとダークのように複数のテーマを持つ場合は、テーマごとに組を登録し、どのテーマでも比を満たすことを確認する。

### 1.4.4 テキストのサイズ変更（Level AA）

[Understanding 1.4.4](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html)

**意図**: 文字を大きくして読む利用者が、内容と機能を失わないようにする。

**必須**

- 支援技術を使わずに文字を 200% まで拡大しても、内容と機能が失われないレイアウトにする。字幕と文字画像は対象外である。

**推奨**

- 文字を入れる領域の高さを固定しない。

**レビュー**

- [ ] 文字を 200% にしたとき、切れる、重なる、操作できなくなる箇所が無いか

**トークン**: 文字サイズを、固定値ではなく拡大に追従する単位で登録する。

### 1.4.5 文字画像（Level AA）

[Understanding 1.4.5](https://www.w3.org/WAI/WCAG22/Understanding/images-of-text.html)

**意図**: 文字を、利用者が大きさや色を変えられる文字として出す。

**必須**

- 同じ見た目を文字で表現できるときは、文字を画像にしない。利用者が見た目を変えられる文字画像と、ロゴのように特定の見た目が本質的なものは除く。

**レビュー**

- [ ] 見出しやボタンの文字が、画像になっていないか

### 1.4.10 リフロー（Level AA）

[Understanding 1.4.10](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

**意図**: 拡大して読む利用者が、縦と横の両方向にスクロールしなくて済むようにする。

**必須**

- 縦にスクロールする内容は、幅 320 CSS ピクセル相当で、情報と機能を失わず、横スクロールなしで使えるようにする。320 CSS ピクセルは、幅 1280 CSS ピクセルの画面を 400% に拡大した幅にあたる。
- 横にスクロールする内容（縦書きなど）は、高さ 256 CSS ピクセル相当で、縦スクロールなしで使えるようにする。
- 地図、図、動画、データ表のように、使うために二次元の配置が必要な部分は、二方向のスクロールを許す。

**推奨**

- 幅の狭い画面のレイアウトから先に設計する。

**レビュー**

- [ ] 幅 320 CSS ピクセルのレイアウトがあるか
- [ ] 横スクロールが残る箇所が、二次元の配置が必要な部分に限られているか

**トークン**: ブレークポイントと、最小幅のレイアウト。

### 1.4.11 非テキストのコントラスト（Level AA）

[Understanding 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)

**意図**: 操作部品とその状態、理解に必要な図形を見分けられるようにする。

**必須**

- 操作部品と、その状態（選択中、フォーカス中など）を見分けるのに必要な視覚情報は、隣接する色とのコントラスト比を 3:1 以上にする。
- 内容の理解に必要な図形の部分（グラフの線、アイコンの形）は、隣接する色とのコントラスト比を 3:1 以上にする。

**例外**

- 非アクティブな部品。ブラウザが見た目を決め、作者が変えていない部品。図の特定の見た目が、伝える情報にとって本質的な場合。

**推奨**

- 境界、選択中、フォーカスを、背景色や影だけで表さない。OS のハイコントラスト設定（Windows の強制カラーモードなど）では、作者の指定した背景色と影が無効になり、それだけで表した境界と状態が消えるためである。線、形、文字のいずれかを併用する。

**レビュー**

- [ ] 入力欄、チェックボックス、トグルの境界が 3:1 以上か
- [ ] 選択中とフォーカス中の見た目が、隣接色と 3:1 以上の差を持つか
- [ ] 情報を伝えるアイコンとグラフが 3:1 以上か

**トークン**: 境界色、フォーカスの線の色、状態色を、隣接する背景との組で登録する。複数のテーマを持つ場合は、テーマごとに組を登録する。

### 1.4.12 テキストの間隔（Level AA）

[Understanding 1.4.12](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html)

**意図**: 利用者が文字の間隔を広げても、内容と機能が失われないようにする。

**必須**

- 次の四つを同時に設定しても、内容と機能が失われないようにする。行の高さを文字サイズの 1.5 倍以上、段落の後の間隔を 2 倍以上、文字の間隔を 0.12 倍以上、単語の間隔を 0.16 倍以上。
- この値をデザインの初期値にする必要はない。利用者が上書きしたときに壊れないことが要件である。
- その言語の表記で使わない間隔（日本語の単語間隔など）は、使う間隔だけで判断する。

**レビュー**

- [ ] 間隔を広げたとき、ボタン、タブ、カードの中の文字が切れないか

### 1.4.13 ホバー又はフォーカスで表示されるコンテンツ（Level AA）

[Understanding 1.4.13](https://www.w3.org/WAI/WCAG22/Understanding/content-on-hover-or-focus.html)

**意図**: ツールチップのように、ホバーやフォーカスで現れる内容が、読む前に消えたり、ほかの内容を塞いだままになったりしないようにする。

**必須**: ホバーかフォーカスで現れ、それを外すと消える内容は、次の三つを満たす。

- 解除できる: ポインタとフォーカスを動かさずに閉じる手段がある。入力エラーを伝える内容と、ほかの内容を隠さない内容は除く。
- ホバーできる: ホバーで現れる内容の上に、消えずにポインタを移せる。
- 持続する: ホバーかフォーカスを外す、利用者が閉じる、内容が無効になる、のいずれかが起きるまで表示を続ける。

**例外**

- ブラウザが見た目を決め、作者が変えていないもの（ブラウザ標準のツールチップなど）。

**レビュー**

- [ ] ポインタを動かさずに、ツールチップを閉じられるか
- [ ] ツールチップの上にポインタを移しても消えないか
- [ ] 一定時間で勝手に消えないか

## 操作可能

### 2.1.1 キーボード（Level A）

[Understanding 2.1.1](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html)

**意図**: ポインタを使えない利用者も、すべての機能を使えるようにする。

**必須**

- すべての機能を、キーボードだけで操作できる設計にする。個々のキー操作に時間の条件を付けない。手書きのように、操作の軌跡そのものが入力である機能は除く。
- ドラッグ、ホバー、スワイプでしか使えない部品には、キーボードで同じ結果に届く操作を設計する。

**レビュー**

- [ ] カルーセル、メニュー、並べ替え、モーダルの操作が、キーボードだけで完了するか

### 2.1.4 文字キーのショートカット（Level A）

[Understanding 2.1.4](https://www.w3.org/WAI/WCAG22/Understanding/character-key-shortcuts.html)

**意図**: 音声入力や打ち間違いで、一文字のショートカットが誤作動しないようにする。

**必須**: 文字、数字、記号のキーだけでショートカットを設けるときは、次のいずれかを満たす。

- 無効にできる。
- 修飾キー（Ctrl、Alt など）を含む組み合わせに割り当て直せる。
- その部品にフォーカスがあるときだけ有効にする。

**レビュー**

- [ ] 一文字のショートカットがあるか。あれば、無効化、割り当て直し、フォーカス時限定のどれかがあるか

### 2.2.1 タイミング調整可能（Level A）

[Understanding 2.2.1](https://www.w3.org/WAI/WCAG22/Understanding/timing-adjustable.html)

**意図**: 読む、入力するのに時間がかかる利用者が、時間切れで作業を失わないようにする。

**必須**: コンテンツが設ける時間制限ごとに、次のいずれかを満たす。

- 解除: 時間制限に達する前に、利用者が解除できる。
- 調整: 時間制限に達する前に、既定の 10 倍以上の範囲で利用者が変えられる。
- 延長: 期限の前に警告し、簡単な操作で延長できる時間を 20 秒以上与える。延長は 10 回以上できる。

ただし、オークションのようにリアルタイムの催しに必須の時間制限、延長すると活動自体が成り立たない時間制限、20 時間を超える時間制限は除く。

**推奨**

- セッションの期限切れは、入力中の内容を残したまま再開できるようにする。

**レビュー**

- [ ] 時間制限ごとに、解除、調整、延長のどれかがあるか

### 2.2.2 一時停止、停止、非表示（Level A）

[Understanding 2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)

**意図**: 動く内容が、ほかの内容を読む妨げにならないようにする。

**必須**

- 自動で始まり、5 秒を超えて続き、ほかの内容と同時に表示される、動く・点滅する・スクロールする内容には、一時停止、停止、非表示のいずれかの手段を置く。
- 自動で始まり、ほかの内容と同時に表示される自動更新には、一時停止、停止、非表示、更新頻度の調整のいずれかの手段を置く。
- 動きや更新が、その活動に本質的な場合は除く。

**推奨**

- OS の「視差効果を減らす」（動きを減らす）設定が有効なときは、装飾の動きと画面遷移の動きを止める。この設定に従うことは Level AAA の 2.3.3 に当たり、AA の要件ではない。

**レビュー**

- [ ] 自動のカルーセル、ティッカー、動画背景に、止める操作があるか

### 2.3.1 3回の閃光、又は閾値以下（Level A）

[Understanding 2.3.1](https://www.w3.org/WAI/WCAG22/Understanding/three-flashes-or-below-threshold.html)

**意図**: 光過敏性の発作を引き起こす閃光を出さない。

**必須**

- どの 1 秒間でも 3 回を超えて閃光する内容を置かない。置く場合は、閃光が一般閃光閾値と赤色閃光閾値を下回るようにする。

**推奨**

- 閃光する表現を使わない。点滅を使う場合も、1 秒間に 3 回以下にする。

**レビュー**

- [ ] 動画、アニメーション、GIF に、1 秒間に 3 回を超える閃光が無いか

### 2.4.1 ブロックスキップ（Level A）

[Understanding 2.4.1](https://www.w3.org/WAI/WCAG22/Understanding/bypass-blocks.html)

**意図**: 全ページで繰り返すヘッダーやナビゲーションを、毎回たどらずに本文へ進めるようにする。

**必須**

- 複数のページで繰り返す内容の塊を飛ばす手段を、少なくとも一つ用意する。本文へ飛ぶリンク、見出し構造、ページ内の領域の区分のいずれでもよい。

**推奨**

- 「本文へ移動」のリンクを置き、フォーカスを受けたときに見えるようにする。

**レビュー**

- [ ] 繰り返しのナビゲーションを飛ばす手段が決まっているか

### 2.4.2 ページタイトル（Level A）

[Understanding 2.4.2](https://www.w3.org/WAI/WCAG22/Understanding/page-titled.html)

**意図**: 開いているページの話題や目的を、タイトルで判別できるようにする。

**必須**

- 各ページに、話題か目的を表すタイトルを付ける。

**推奨**

- サイト内のページごとに異なるタイトルにする。個別の内容を先に、サイト名を後に置く。

**レビュー**

- [ ] 画面ごとのタイトルが、仕様に書かれているか

### 2.4.3 フォーカス順序（Level A）

[Understanding 2.4.3](https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html)

**意図**: キーボードで順に移動したときに、意味と操作が崩れないようにする。

**必須**

- 順に移動する順序が意味や操作に関わるときは、意味と操作性を保つ順序でフォーカスを移す。

**推奨**

- 視覚上の読む順とフォーカスの順を一致させる。左から右に書く言語では、左上から右下へ進む順が読む順と一致しやすい。
- モーダルやメニューを開いたときは、開いた操作の直後にフォーカスを移し、閉じたら開いた操作に戻す。

**レビュー**

- [ ] フォームや段組みで、フォーカスの順が仕様に書かれているか
- [ ] 関係のない区画を行き来する順になっていないか

### 2.4.4 リンクの目的（コンテキスト内）（Level A）

[Understanding 2.4.4](https://www.w3.org/WAI/WCAG22/Understanding/link-purpose-in-context.html)

**意図**: リンクの行き先を、リンクの文字か、その文脈から判断できるようにする。

**必須**

- 各リンクの目的を、リンクの文字だけで、またはリンクの文字と、同じ文や段落などの文脈とをあわせて判断できるようにする。

**推奨**

- 文脈に頼らず、リンクの文字だけで行き先が分かるようにする。「こちら」「詳細」「もっと見る」だけのリンクを置かない。

**レビュー**

- [ ] リンクの文字と周囲の文で、行き先が分かるか
- [ ] 同じ文字で行き先の違うリンクが、同じ画面に並んでいないか

### 2.4.5 複数の手段（Level AA）

[Understanding 2.4.5](https://www.w3.org/WAI/WCAG22/Understanding/multiple-ways.html)

**意図**: 利用者が自分に合う方法で、目的のページを見つけられるようにする。

**必須**

- サイト内の各ページに、二つ以上の方法で到達できるようにする。ナビゲーション、検索、サイトマップ、目次、関連ページへのリンクなどから選ぶ。手続きの途中の段と、手続きの結果のページは除く。

**レビュー**

- [ ] ページを見つける方法が二つ以上あるか

### 2.4.6 見出し及びラベル（Level AA）

[Understanding 2.4.6](https://www.w3.org/WAI/WCAG22/Understanding/headings-and-labels.html)

**意図**: 見出しとラベルから、その区画や入力欄の話題と目的が分かるようにする。

**必須**

- 見出しとラベルを置く場合は、話題か目的を表す文言にする。

**レビュー**

- [ ] 見出しだけを拾い読みして、各区画の内容が分かるか
- [ ] ラベルから、入れる内容が分かるか

### 2.4.7 フォーカスの可視化（Level AA）

[Understanding 2.4.7](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html)

**意図**: キーボードで操作する利用者が、いまどこにフォーカスがあるか分かるようにする。

**必須**

- キーボードで操作できるすべての部品に、フォーカスの位置が見える状態を設計する。ブラウザの標準表示を消す場合は、代わりの表示を設計する。

**推奨**

- フォーカスの表示は、部品を囲む線にして、隣接色とのコントラスト比を 3:1 以上にする。1.4.11 の状態のコントラストも満たしやすくなる。
- 一色の線では、明るい背景と暗い背景（濃い色のボタンやダークテーマ）の両方で 3:1 を保てないことがある。その場合は、明るい色と暗い色の線を二重に重ね、どちらかが隣接色と 3:1 以上になるようにする。

**レビュー**

- [ ] すべての操作部品に、フォーカス時の見た目があるか
- [ ] ホバーの見た目と、フォーカスの見た目を取り違えていないか

**トークン**: フォーカスの線の色、太さ、部品との間隔。

### 2.4.11 フォーカスの非遮蔽（最低限）（Level AA）

[Understanding 2.4.11](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)

**意図**: フォーカスを受けた部品が、作者の置いた固定ヘッダーやバナーに完全に隠れないようにする。

**必須**

- フォーカスを受けた部品が、作者の置いた内容で完全には隠れないようにする。利用者が開いた内容で隠れても、フォーカスを動かさずに表示できるなら問題にしない。

**レビュー**

- [ ] 固定ヘッダー、固定フッター、Cookie バナー、チャットの起動ボタンの下に、フォーカスが完全に隠れる箇所が無いか

### 2.5.1 ポインタのジェスチャ（Level A）

[Understanding 2.5.1](https://www.w3.org/WAI/WCAG22/Understanding/pointer-gestures.html)

**意図**: 複数の指や、軌跡をなぞる操作ができない利用者も使えるようにする。

**必須**

- ピンチなどの複数点の操作や、スワイプなどの軌跡に依存する操作で動く機能は、一点のポインタで、軌跡によらない操作（タップ、クリック）でも使えるようにする。その操作が本質的な場合は除く。

**レビュー**

- [ ] スワイプ、ピンチで動く機能に、ボタンでの代わりがあるか

### 2.5.2 ポインタのキャンセル（Level A）

[Understanding 2.5.2](https://www.w3.org/WAI/WCAG22/Understanding/pointer-cancellation.html)

**意図**: 誤って押した操作を、指を離す前に取り消せるようにする。

**必須**: 一点のポインタで使う機能は、次のいずれかを満たす。

- 押し下げた時点では実行しない。
- 離した時点で完了し、完了前に中止する手段か、完了後に元に戻す手段がある。
- 離したときに、押し下げで起きた結果が元に戻る。
- 押し下げで実行することが本質的である（鍵盤の演奏など）。

**レビュー**

- [ ] 押した瞬間に確定する操作が無いか

### 2.5.3 ラベルを含む名前（Level A）

[Understanding 2.5.3](https://www.w3.org/WAI/WCAG22/Understanding/label-in-name.html)

**意図**: 音声で操作する利用者が、見えているラベルを読み上げれば操作できるようにする。

**必須**

- 文字か文字画像のラベルを持つ部品は、支援技術に渡す名前に、見えているラベルの文字を含める。

**推奨**

- 名前の先頭に、見えているラベルを置く。

**レビュー**

- [ ] 見えるラベルと、支援技術に渡す名前が食い違っていないか

### 2.5.4 動きによる起動（Level A）

[Understanding 2.5.4](https://www.w3.org/WAI/WCAG22/Understanding/motion-actuation.html)

**意図**: 端末を振る、傾けるといった操作ができない利用者や、誤作動を防ぎたい利用者に配慮する。

**必須**

- 端末や体の動きで動く機能は、画面上の部品でも操作できるようにし、動きへの反応を無効にできるようにする。動きが本質的な場合は除く。

**レビュー**

- [ ] 振る、傾けるで動く機能に、ボタンでの代わりと無効化があるか

### 2.5.7 ドラッグ動作（Level AA）

[Understanding 2.5.7](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)

**意図**: ドラッグが難しい利用者も、同じ機能を使えるようにする。

**必須**

- ドラッグで操作する機能は、ドラッグなしの一点のポインタ操作でも実行できるようにする。ドラッグが本質的な場合と、ブラウザが決める機能で作者が変えていない場合は除く。

**推奨**

- 並べ替えには「上へ」「下へ」の操作、スライダーには値の入力か増減ボタン、ファイルの投入には選択ボタンを置く。

**レビュー**

- [ ] ドラッグする部品すべてに、タップかクリックで同じ結果に届く操作があるか

### 2.5.8 ターゲットのサイズ（最低限）（Level AA）

[Understanding 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

**意図**: 小さく密集した操作対象を、誤って押さないようにする。

**必須**

- ポインタで操作する対象を、24 × 24 CSS ピクセル以上にする。

**例外**

- 間隔: 24 CSS ピクセル四方に満たない対象は、各対象のバウンディングボックスの中心に直径 24 CSS ピクセルの円を置いたとき、その円がほかの対象にも、ほかの小さい対象の円にも交差しない。
- 同等: 同じページに、同じ機能を持ち、この基準を満たす別の部品がある。
- インライン: 対象が文中にあるか、周囲の文字の行の高さで大きさが決まる。
- ブラウザの制御: 大きさをブラウザが決め、作者が変えていない。
- 本質的: 対象のその表示が、伝える情報に本質的であるか、法律で求められている。

**推奨**

- 主要な操作は 44 × 44 CSS ピクセル以上にする。これは Level AAA の 2.5.5 ターゲットのサイズ（拡張）の値である。

**レビュー**

- [ ] ボタン、アイコンボタン、チェックボックスが 24 × 24 CSS ピクセル以上か
- [ ] 小さい対象の円が、隣の対象や隣の円に交差していないか

**トークン**: 操作対象の最小サイズ、アイコンボタンのヒット領域、対象の間隔。

## 理解可能

### 3.1.1 ページの言語（Level A）

[Understanding 3.1.1](https://www.w3.org/WAI/WCAG22/Understanding/language-of-page.html)

**意図**: 読み上げが、ページの主な言語の発音で読めるようにする。

**必須**

- 各ページの主な言語を仕様に書く。

**レビュー**

- [ ] 画面ごとの主な言語が決まっているか

### 3.1.2 一部分の言語（Level AA）

[Understanding 3.1.2](https://www.w3.org/WAI/WCAG22/Understanding/language-of-parts.html)

**意図**: ページ内で別の言語に切り替わる部分を、その言語で読めるようにする。

**必須**

- 主な言語と違う言語の文や句を、仕様で特定する。固有名詞、専門用語、言語の決まらない語、周囲の文章で一般語として定着した語は除く。

**レビュー**

- [ ] 外国語の引用や、言語の切り替えの場所が書かれているか

### 3.2.3 一貫したナビゲーション（Level AA）

[Understanding 3.2.3](https://www.w3.org/WAI/WCAG22/Understanding/consistent-navigation.html)

**意図**: 複数のページで繰り返すナビゲーションを、毎回同じ順で探せるようにする。

**必須**

- 複数のページで繰り返すナビゲーションは、繰り返すたびに同じ相対的な順序で並べる。利用者が変更した場合は除く。

**推奨**

- 順序に加えて、画面上の位置も揃える。

**レビュー**

- [ ] グローバルナビゲーションとフッターの項目順が、全ページで同じか

### 3.2.4 一貫した識別性（Level AA）

[Understanding 3.2.4](https://www.w3.org/WAI/WCAG22/Understanding/consistent-identification.html)

**意図**: 同じ機能の部品を、どのページでも同じものとして認識できるようにする。

**必須**

- サイト内で同じ機能を持つ部品は、一貫した名前、ラベル、アイコンで示す。

**レビュー**

- [ ] 検索、保存、閉じるなどが、ページによって違う名前やアイコンになっていないか

**トークン**: アイコンと名前の対応表。

### 3.2.6 一貫したヘルプ（Level A）

[Understanding 3.2.6](https://www.w3.org/WAI/WCAG22/Understanding/consistent-help.html)

**意図**: 助けを求める手段を、どのページでも同じ順で見つけられるようにする。

**必須**

- 問い合わせ先、人への連絡手段、自己解決の手段（FAQ など）、自動応答の連絡手段のいずれかを複数のページに置くときは、ページ内のほかの内容に対して同じ順序で置く。利用者が変更した場合は除く。

**推奨**

- 同じ画面幅のレイアウトでは、画面上の位置も揃える。

**レビュー**

- [ ] ヘルプへの入口が、全ページで同じ順序の場所にあるか

### 3.3.1 エラーの特定（Level A）

[Understanding 3.3.1](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html)

**意図**: 自動で見つけた入力の誤りを、どの項目で何が誤りかまで伝える。

**必須**

- 入力の誤りを自動で検出したときは、誤りのある項目を特定し、誤りの内容を文字で示す。

**推奨**

- 送信時に複数の誤りを見つけたときは、画面の上部に誤りの件数と各項目へのリンクを並べ、最初の誤りの項目へフォーカスを移す。誤りが画面の外にあると、利用者は送信が失敗したことにも気づけないためである。

**レビュー**

- [ ] エラーの状態のデザインに、項目の特定と、文字での説明があるか

**トークン**: 入力欄のエラー状態、エラー文の位置。

### 3.3.2 ラベル又は説明（Level A）

[Understanding 3.3.2](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html)

**意図**: 入力を求める場面で、何をどう入れるかを先に分かるようにする。

**必須**

- 利用者の入力を求める箇所に、ラベルか説明を置く。

**推奨**

- 形式の決まった入力（日付、電話番号）は、形式を入力欄の近くに先に書く。
- プレースホルダーをラベルの代わりにしない。入力を始めると消えるためである。
- 必須か任意かは、「必須」「任意」の文字で示す。「*」の記号や色だけで示すと、記号の意味を知らない利用者と色を見分けにくい利用者に伝わらない。

**レビュー**

- [ ] すべての入力欄に、ラベルか説明があるか

### 3.3.3 エラー修正の提案（Level AA）

[Understanding 3.3.3](https://www.w3.org/WAI/WCAG22/Understanding/error-suggestion.html)

**意図**: 誤りを見つけたときに、直し方まで伝える。

**必須**

- 入力の誤りを自動で検出し、修正の候補が分かっているときは、その候補を示す。セキュリティや内容の目的を損なう場合は除く（パスワードの正解を示さない、など）。

**レビュー**

- [ ] エラー文に、直し方が書かれているか。「入力が無効です」ではなく「メールアドレスに @ を含めてください」になっているか

### 3.3.4 エラー回避（法的、金融、データ）（Level AA）

[Understanding 3.3.4](https://www.w3.org/WAI/WCAG22/Understanding/error-prevention-legal-financial-data.html)

**意図**: 契約、支払い、データの変更や削除、試験の回答の送信で、取り返しのつかない誤りを防ぐ。

**必須**: 該当する送信について、次のいずれかを満たす。

- 取り消せる: 送信を取り消せる。
- 確かめる: 入力の誤りを確かめ、利用者が直す機会がある。
- 確認する: 送信を確定する前に、内容を確認し、直す手段がある。

**レビュー**

- [ ] 支払い、契約、削除の流れに、取り消し、確かめ、確認のどれかがあるか

### 3.3.7 冗長な入力（Level A）

[Understanding 3.3.7](https://www.w3.org/WAI/WCAG22/Understanding/redundant-entry.html)

**意図**: 同じ手続きの中で、すでに伝えた情報をもう一度打たせない。

**必須**

- 同じ手続きの中で、利用者が前に入力した情報、または利用者に提示した情報を再び求めるときは、自動で入力するか、選べるようにする。
- 再入力が本質的な場合、セキュリティのために必要な場合、前の情報が無効になった場合は除く。

**レビュー**

- [ ] 配送先と請求先のように、同じ情報を二度打たせる箇所に、自動入力か選択肢があるか

### 3.3.8 アクセシブルな認証（最低限）（Level AA）

[Understanding 3.3.8](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html)

**意図**: 記憶、転記、計算、パズルが苦手な利用者も、ログインできるようにする。

**必須**: 認証のどの段でも、認知機能テスト（パスワードを覚える、文字を書き写す、パズルを解くなど）を求めるときは、その段が次のいずれかを満たす。

- 代わりの方法: 認知機能テストに頼らない別の認証方法がある。
- 支援する仕組み: テストを済ませるのを支援する仕組みがある。パスワードマネージャーによる入力と、コピー＆ペーストが例である。
- 物の認識: テストが、物を見分ける内容である（車の写った画像を選ぶなど）。
- 個人の内容: テストが、利用者自身がサイトに渡した文字以外の内容（自分で登録した画像など）を見分ける内容である。

**推奨**

- 物の認識と個人の内容による方法も、使わずに済むようにする。Level AAA の 3.3.9 は、この二つを例外にしない。

**レビュー**

- [ ] パスワードと確認コードの欄に、貼り付けとパスワードマネージャーが使えるか
- [ ] 確認コードを一文字ずつ別の欄に打たせていないか
- [ ] 文字を書き写す CAPTCHA や計算の CAPTCHA に、別の方法があるか

## 実装で担保する基準

次の基準は、デザインの判断ではなく、実装の書き方で適合が決まる。デザインの仕様では、名前、役割、状態を部品ごとに書いておくと実装者が満たしやすい。

- 1.3.5 入力目的の特定（Level AA）: 利用者自身の情報を集める入力欄の目的を、プログラムで判別できるようにする。
- 2.1.2 キーボードトラップなし（Level A）
- 3.2.1 フォーカス時（Level A）、3.2.2 入力時（Level A）: フォーカスや入力だけで、予告なく画面の文脈を変えない。デザインでは、選んだだけで画面が切り替わるメニューを作らないことに当たる。
- 4.1.2 名前、役割、値（Level A）
- 4.1.3 ステータスメッセージ（Level AA）: 保存完了などの通知を、フォーカスを移さずに支援技術へ伝える。

4.1.1 構文解析は、WCAG 2.2 で削除された。
