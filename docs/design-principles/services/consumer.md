# toCサービス

個人が、自分のために使う画面に使う。初回の訪問と、その後の利用の両方を含む。契約組織の担当者が日常業務で開く画面は [SaaS](./saas.md)、運用台帳は [管理画面](./admin.md) を使う。

主タスクは、その題材で個人がしたいことを、短い注意で終わらせることにある。この文書では、ページを開いてスクロールせずに見える範囲を第一画面と呼び、スマートフォンのように片手で持って操作する端末の画面を手で持つ画面と呼ぶ。第一画面は、その題材に特有のものが見える場所にする。統計の大きな数字、グラデーション、どの題材にも使えるカードの並びを、題材の代わりに置かない。

## 原則のどこを上書きするか

| 原則のルール | toC での扱い |
| --- | --- |
| 読み順と優先度 | 第一画面では、題材に特有のものを最初に置く。F 字と Z 字は、文章やキャンペーンのページに限って使う |
| 削る | 記憶に残す要素は一つにする。それ以外の飾りは削る。空の画面には次の操作を残してよい |
| 操作の幾何 | 手で持つ画面では、主要な操作を親指の届く側へ置く。24 CSS ピクセルは下限で、主操作はそれより大きくする |
| 短い経路 | 二回目以降の同じ操作に必須。初回の説明をショートカットで飛ばせるようにし、初回の主経路からは外さない |
| 文言 | 販売のコピーより、何が起きるかを優先する。原則の文言ルールより、このファイルの文面の規則を優先する |
| まとまり、判別、配置、状態、誤り、再認、一貫性、助けの場所、一度に出す数 | 原則どおり |

## 必須

- 第一画面の主要素を、そのサービスの題材から選ぶ。見出し、画像、実データの一例、操作の結果の見本のいずれかにする。題材と無関係な装飾を主要素にしない。
- 主操作は、画面につき一つを見た目で最優先にする。同じ強さのボタンを並べない。
- 主操作のラベルは、押したあとに起きることとする。「送信」「こちら」にしない。流れの中では同じ動詞を保ち、完了の通知もその動詞に合わせる。
- アカウント作成、支払い、個人情報の送信は、何に使うかを操作の前に書く。条件は、同意のチェックを入れたあとに初めて出さない。
- 支払いと削除は、対象と金額または失われるものを、確認の段でもう一度見せる。
- 空の画面とエラーは、次にできる操作を一つ書く。利用者の心情を代弁する文で埋めない。
- 手で持つ画面では、主操作を画面の下部か、内容の直下に置く。届かない側だけに置かない。
- 自動で動く要素は、注意を引く理由がある一つに限る。利用者が起こした操作への応答は、この数に含めない。

## 推奨

- 本文を読む画面では、行が長すぎて行頭へ戻れなくならない幅にする。英語の組版では 80 字未満が目安として使われる。日本語の行は、それより短く組む。
- 書体は一つ、役割が違うときだけ二つまでにする。二つにするときは、見出しと本文の差がはっきり分かる組み合わせにする。
- 見出しの中の一語だけを色や斜体で抜かない。ラベルをすべて大文字にしない。
- 番号付きの印は、手順や時系列であるときだけ付ける。

## 見た目

配色は、題材の材料や場面から選ぶ。背景、文字、主操作、危険の四つの役割を先に決める。アクセントを増やすときは、記憶に残す一つの要素にだけ使う。

大胆にしてよいのはその一つの要素で、周囲の余白、ボタン、本文は同じ規則で静かに組む。

レイアウトは、題材の主要素、短い説明、主操作、の順を基本にする。説明が主要素より面積を取らないようにする。

どの題材にも共通の、生成りの背景とテラコッタ、黒地に蛍光色、同じ角丸と薄い影のカードの敷き詰めは、題材がその見た目であるとき以外は使わない。詳細は [サービス別の特化ルール](./README.md) の視覚の決め方に従う。

## 文言

- 利用者の言葉で、ものの名前を書く。内部の仕組みの名前を出さない。
- 一つの文要素には、一つの仕事だけをさせる。見出しが説明を兼ねて長くならないようにする。
- エラーは、何が起きて、データが残っているかを書く。謝罪を置かない。
- 語調は、その題材の相手に合わせる。巧みな言い換えより、初見で意味が取れる文にする。
