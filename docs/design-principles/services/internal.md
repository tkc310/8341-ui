# 社内向けツール

自社の社員が、自分の業務手続きを完了するための画面に使う。申請、承認、参照、届出が中心である。顧客アカウントを持たない。毎日開く台帳の運用は [管理画面](./admin.md) を使う。

主タスクは、その手続きを、手順を覚えなくても、その場の説明だけで終わらせることにある。見た目の個性は、社内の既存画面と揃えることより後に置く。

## 原則のどこを上書きするか

| 原則のルール | 社内向けでの扱い |
| --- | --- |
| 削る | 手続きに必要な規程、期限、添付の条件は残す。キャンペーン用の要素は置かない |
| 一度に出す数 | 申請の入力は段に分ける。承認者の選択肢が組織規模で多くなるときは、検索付きの選択にする |
| 一貫性 | 公開ウェブの慣行より、社内で既に使われている用語と画面の位置を優先する |
| 助けの場所 | 全社の問い合わせ先を、各手続きの中にも書く。ポータルの隅だけに置かない |
| 短い経路 | 毎日使う手続きに限って必須にする。年に数回の手続きは、短い経路より手順の説明を優先する |
| 読み順、まとまり、判別、配置、状態、誤り、再認、文言 | 原則どおり |

ジャコブの法則が言う「他のサイトと同じ」は、フォームの基本操作に限って残す。ナビゲーションの情報設計は、社内ポータルの既存に合わせる。

## 必須

- 画面の最初に、この手続きで何が決まり、いつまでに終えるかを書く。
- 入力は、社員が持っている情報の順に並べる。システムの内部工程の順に並べない。
- 承認が必要な手続きは、今どの段階で、誰の判断待ちかを、申請者の画面に出す。
- 差戻しは、どの項目を直すかと、コメントを同じ場所に出す。最初から入れ直しにしない。
- 添付、上長、金額のように、規程で決まっている制約は、項目のそばに書く。送信後のエラーだけにしない。
- 代理申請と本人申請を分けられる手続きは、誰の名義で出すかを最初に選ばせる。
- 完了画面には、受付番号と、次に自分が起こす操作が無いかを書く。
- 年に数回しか使わない手続きには、各段に短い説明を残す。毎日使う手続きは、説明を項目の補足に下げる。

## 推奨

- 下書きを残し、途中から再開できるようにする。
- 過去の自分の申請を、新規作成の初期値に使えるようにする。
- 組織変更で承認者が消えたときは、申請者が次の相手を選べるようにする。

## 見た目

配色と書体は、社内で既にあるポータルに合わせる。新しいアクセントを、このツールだけのために増やさない。

レイアウトは、左または上に手続きの段、中央に今の入力、という順にする。マーケティング用のヒーローは置かない。段の番号は、実際に順番があるときだけ使う。

角丸のカードを、入力欄の一つずつに被せない。一つの段を一つの領域にする。

動きは、保存と送信の結果を示すものに限る。

## 文言

- 部門と役職は、社員が社内で呼ぶ名前にする。
- ボタンは手続きの動詞にする。「申請する」「承認する」「差し戻す」。
- 規程の引用は、全文を貼らず、判断に必要な条件と、規程の名前を書く。
- エラーに謝罪を置かない。直す項目と、受付窓口を書く。

## レビュー

- [ ] 入力順が、社員の持っている情報の順か
- [ ] 承認の現在地と差戻し箇所が、申請者から見えるか
- [ ] まれにしか使わない手続きに、段ごとの説明があるか
- [ ] 見た目が、社内の既存画面から外れていないか
- [ ] 完了後に、受付番号と次の操作が分かるか

## トークン

手続きの段、必須と任意、差戻し、下書き、完了。色は社内ポータルの意味づけを流用し、このツール独自の状態色を増やさない。
