# SaaS

契約した組織が、継続して日常業務に使う製品の画面に使う。利用者ロールが複数あり、初期設定と日常作業が分かれている。同じ製品の中の運用台帳は [管理画面](./admin.md) を使う。

主タスクは、契約組織の担当者が、毎回の作業を短く終えることにある。初回だけ、作業を始められる状態まで連れていく。毎日開く画面で、視覚の実験をしない。

## 原則のどこを上書きするか

| 原則のルール | SaaS での扱い |
| --- | --- |
| 削る | データが無い最初の画面には、次の一つの操作を残す。日常画面の飾りは削る |
| 読み順と優先度 | 日常画面にヒーローを置かない。記憶に残してよい強調は、製品につき一つの場面に限る |
| 短い経路 | 日常作業では必須。初期設定のウィザードでは、基本の順を崩すショートカットを主操作にしない |
| 自律的な処理の範囲 | 推薦、自動分類、下書き生成がある製品では必須にする |
| 一貫性 | ページごとの個性より、製品内の同じ機能を同じ部品にすることを優先する |
| 一度に出す数、まとまり、判別、配置、状態、誤り、再認、文言、助けの場所 | 原則どおり |

## 必須

- 日常画面と設定画面を分ける。設定への入口は同じ位置に置き、日常の主操作と混ぜない。
- データが一つも無い状態では、その画面で最初に行う操作を一つだけ出す。説明文を操作より上に長く置かない。
- ロールによって見えない機能は、権限の名前で理由が分かるようにする。有料プランでロックするものは、制限と、変更に必要な権限者を書く。
- 請求、削除、メンバー除外、外部への公開は、確認の段で対象の名前を繰り返す。
- 他のメンバーが同じレコードを編集しうる画面は、保存時に衝突したことが分かる表示を出す。
- 初回の設定は、完了しなくても日常画面へ進める項目と、進む前に必須の項目を分ける。
- 製品内の主操作の名前を、ボタン、メニュー、完了通知で揃える。
- 推薦や自動下書きを出す画面は、人が確定するまで反映しない。止める操作と、自動で入った箇所の表示を置く。

## 推奨

- 直近の作業へ戻る入口を、サインイン後の最初の画面に置く。
- 設定の検索を、設定項目が増えた製品では用意する。
- 試用の残数や期限は、主操作を遮るモーダルではなく、作業領域の端に置く。

## 見た目

毎日使う画面は、背景、文字、境界、主操作、状態の役割色で組む。題材に由来する色は、主操作か、製品につき一つの強調場面に限って使う。

書体は、UI 用を一つにする。マーケティング面と製品内画面を同じサイトに置く場合だけ、表示用をもう一つ追加してよい。三つ目は置かない。

同じ種類のレコードが並ぶときだけ、同じカードを繰り返してよい。設定フォームや記事の節を、見た目を揃えるためだけにカードへ分割しない。影と角丸を、画面の全部の領域に同じ値で掛けない。

動きは、操作の結果（開く、畳む、保存した）に使う。セクションごとの浮上は、日常画面では使わない。

## 文言

- 利用者の作業語を使う。「Webhook の設定」ではなく、その製品で利用者の仕事が「通知の送信先」なら、その語を使う。
- 空の画面は、気分の文ではなく、次の操作を書く。
- プランの制限は、できないことを先に書き、その次に変更の手順を書く。
- エラーに謝罪を置かない。失敗した操作と、残っているデータの状態を書く。

## レビュー

- [ ] 日常の主操作と設定が分かれているか
- [ ] 空の画面に、次の操作が一つだけあるか
- [ ] 権限とプランの制限が、押す前に分かるか
- [ ] 破壊的操作の確認に、対象の名前があるか
- [ ] 自動で入った内容を、人が確定するまで反映していないか
- [ ] 毎日開く画面に、ヒーローや画面入場の連続した動きが無いか

## トークン

作業領域と設定領域、空状態、主操作、権限で押せない状態、プラン制限のバナー、破壊的操作。空状態用のイラストを置く場合も、トークンはレイアウトとボタンに限る。
