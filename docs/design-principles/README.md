# デザイン原則

このディレクトリには、ウェブの画面を設計するためのルールを自然言語で置く。デザインシステムや DESIGN.md を新規作成するとき、既存のものを調整するとき、既存の画面を評価・レビューするときに、AI エージェントと開発者が参照する。特定のフレームワークや実装技術には依存しない。

## どれを先に読むか

画面を設計するときは、次の順でルールを適用する。

1. [UI の方向性の選択](./ui-orientation.md)。画面をオブジェクト指向 UI にするかタスク指向 UI にするかを、ドメインと対象ユーザーから決める。この判断は、ナビゲーションの構成と主要画面の設計に影響する。
2. [サービス別の特化ルール](./services/README.md)。管理画面、社内向けツール、SaaS、toC のどれかに当たる画面では、特化ルールを先に満たす。原則と食い違う判断は、特化ルールを採る。
3. [ウェブデザインの原則](./principles.md)。UI の方向性と特化ルールが書いていない判断に使う。
4. [デザイン段階で決める WCAG 2.2 の達成基準](./wcag-for-designers.md)。この文書の必須は、UI の方向性、特化ルール、原則のいずれからも緩めない。特化ルールが達成基準より厳しいときは、特化ルールを採る。

## ルールの強さ

各文書のルールには「必須」と「推奨」を付けている。強さは文書によって次のように違う。

| ルール | DESIGN.md での扱い |
| --- | --- |
| WCAG の必須 | 外せない。緩めることもできない |
| 特化ルールと原則の必須 | 原則として採る。外すときは、外す理由を DESIGN.md に書く |
| 推奨 | プロダクトごとに採るかどうかを決める |

## 収録内容

### [UI の方向性の選択](./ui-orientation.md)

画面をオブジェクト指向 UI にするかタスク指向 UI にするかの選択基準を置く。ドメインの専門性と対象ユーザーの習熟度、ナビゲーションの見え方から判断する。方向性は、ナビゲーション、主要画面、空状態の設計に影響する。一つのプロダクトに両方の画面があるときは、画面ごとに選ぶ。

### [サービス別の特化ルール](./services/README.md)

画面の目的ごとに、原則より優先するルールを置く。一つのプロダクトに複数の種類の画面があるときは、画面ごとに文書を選ぶ。

- [管理画面](./services/admin.md)
- [社内向けツール](./services/internal.md)
- [SaaS](./services/saas.md)
- [toC サービス](./services/consumer.md)

### [ウェブデザインの原則](./principles.md)

前半の適用ルールは、判断の対象が重複しない十五の項目である。読み順と優先度、まとまり、文字と図の判別、配置の秩序、操作の幾何、一度に出す数、一貫性、状態と応答、誤りと撤回、再認、文言、削る、助けの場所、短い経路、自律的な処理の範囲。各項目に出典、必須と推奨、レビュー項目、トークンへの対応を付けている。

後半の出典のカタログは、次の枠組みの中身と、どの適用ルールへ吸収したかを示す。ビジュアルデザインの基本原則、ニールセンのユーザビリティ 10 原則、フィッツ・ヒック・ミラーの法則、デジタル庁のユーザビリティデザインの原則、ゲシュタルトの法則、F 字型と Z 字型の視線パターン、ジャコブの法則、連続位置効果、フォン・レストルフ効果、ドハティのしきい値。

紙面のデザインと調査の手順は、適用ルールに入れていない。アクセシビリティの数値は WCAG の文書に置く。

出典のうち外部の文書は、この文書で使う範囲に絞った要約を [sources/](./sources/README.md) に置く。リンクが切れたときは、要約を手がかりに代わりの文書を探す。

### [デザイン段階で決める WCAG 2.2 の達成基準](./wcag-for-designers.md)

WCAG 2.2 の Level A と AA の達成基準のうち、配色、文字、レイアウト、部品の振る舞い、文言、画面の流れを決めた時点で適合がほぼ決まるものを並べる。必須には達成基準の本文が要求する内容だけを書き、それより厳しい選択は推奨に分けている。実装の書き方だけで決まる基準は、末尾に名前だけを置く。

## 使い方

### デザインシステムまたは DESIGN.md を新規作成する

1. 画面の方向性（オブジェクト指向 UI かタスク指向 UI か）を、ドメインと対象ユーザーから決める。
2. 画面の目的に合う特化ルールを選ぶ。
3. 特化ルールが書いていない判断を、原則から補う。
4. 達成基準の値は WCAG の文書から入れる。特化ルールのほうが厳しい項目は、特化ルールの値を使う。
5. 必須を外す項目には、外す理由を書く。
6. トークン名とコンポーネント名を定める。

### 複数のプロダクトで共有する基盤のデザインシステムを作る

特定のプロダクトに属さず、複数のプロダクトで使い回すデザインシステムは、UI の方向性とサービス種別をまだ決められない。方向性とサービス種別は、それを使う各プロダクトの DESIGN.md で決める。基盤の側では次のように進める。

1. 原則と WCAG の必須を、トークンとコンポーネントの契約に落とす。原則の各ルールが、どのトークンとコンポーネントで満たされるかの対応表を基盤の DESIGN.md に書く。
2. 特化ルールが要求する部品とトークンを、どのサービス種別でも組み立てられるように用意する。管理画面の等幅の識別子と状態色、toC の主操作のサイズのように、特化ルールの「トークン」節に挙がるものを確認する。
3. 特定のサービス種別に寄った見た目（密集した表、大きな第一画面の要素など）は、基盤の既定にしない。必要なプロダクトの側で組み立てる。
4. ライトとダークのように複数のテーマを持つ場合は、テーマごとに WCAG の必須を確認する。
5. 基盤の DESIGN.md には、UI の方向性とサービス種別を「各プロダクトで決める」と書き、プロダクト側の DESIGN.md の雛形を添える。

### 既存のデザインシステムまたは DESIGN.md を調整する

1. 画面の方向性が適切か確認する。ドメインと対象ユーザーが変わった場合は、方向性を見直す。
2. 画面の目的に合う特化ルールを選び、既存のトークンとコンポーネントを照合する。
3. 特化ルールが書いていない項目を、原則と照合する。
4. WCAG の必須を満たさない定義を直す。
5. 不足している定義を、優先順位の高いルールから追加する。

### 既存の画面やデザインを評価・レビューする

1. 各ルールのレビュー項目（チェックリスト）を使い、画面が基準を満たすか確認する。
2. WCAG の必須項目を満たさない箇所を特定する。
3. 特化ルールと原則の必須を満たさない箇所を特定し、外す理由が明示されているか確認する。
4. 優先順位（UI の方向性 → 特化ルール → 原則 → WCAG）に沿って、改善の優先度を決める。

### AI エージェントに渡す

これらの文書をコンテキストとして渡すと、エージェントに次の作業をさせられる。

- デザインシステムまたは DESIGN.md の新規作成
- トークンとコンポーネントの生成と、既存のものとの照合
- 各ルールのレビュー項目に沿ったデザインレビュー
- アクセシビリティ要件の確認と改善提案

#### スキルとして使う（Claude Code・Cursor・Codex）

8341-ui のリポジトリでは、このディレクトリのルールをスキルとして使える。スキルの置き場所とエージェントごとの読み込み方は [8341-ui の docs/ai-agents.md](https://github.com/tkc310/8341-ui/blob/main/docs/ai-agents.md) に書いている。

**スキル**: `design-principles`（`.claude/skills/design-principles/SKILL.md`）
- デザイン作業時に読み込まれる手順とルーター
- 作業モードに応じて必要なルールだけを読み込む（プログレッシブディスクロージャー）
- すべてのモードで、最初に前提条件をヒアリングする（`hearing.md` 参照）
- スキルの `references/` は、このディレクトリへのシンボリックリンクである

**モードごとのスキル**（スラッシュコマンドとしても呼べる）:
- `/design-init` - 新規デザインシステムまたは DESIGN.md を作成
- `/design-adjust` - 既存システムの調整・更新
- `/design-review` - デザインレビューの実施

#### 8341-ui を使うプロダクトで使う

`npx shadcn@latest add @8341/design-md` を実行すると、このディレクトリがプロダクトの `docs/design-principles/` に、各ルールの必須をまとめた DESIGN.md がリポジトリ直下に置かれる。プロダクトの前提（UI の方向性、サービス種別、外した必須）は、その DESIGN.md に書く。配られたこのディレクトリは直接編集しない。

**ルールへのフィードバック**: 対話中にルールの改善点（ギャップ、曖昧さ、適合しないルール、繰り返される例外）が見つかった場合、エージェントがユーザーに伝え、[8341-ui](https://github.com/tkc310/8341-ui) の `docs/design-principles/` への編集を提案する。プロダクト固有の例外は、そのプロダクトの DESIGN.md に記録する。

## 注意事項

- WCAG の基準は、W3C 勧告（2024年12月12日版）の WCAG 2.2 に基づく。改訂の有無は [W3C のクイックリファレンス](https://www.w3.org/WAI/WCAG22/quickref/) で確認する。
- 出典の要約は、このリポジトリで選んだ範囲に限る。原典の全体を写したものではない。
