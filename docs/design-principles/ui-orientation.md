# UI の方向性の選択

画面設計の前段階で、その画面をオブジェクト指向 UI にするかタスク指向 UI にするかを決める。この選択は、ナビゲーションの構成、主要画面の設計、空状態の表示に影響する。

この文書の判断は、[サービス別の特化ルール](./services/README.md) および [ウェブデザインの原則](./principles.md) より前に適用する。方向性が決まったあとで、各画面の具体的な設計に特化ルールと原則を使う。

## 二つの方向性

### オブジェクト指向 UI

ドメインの対象（名詞）を中心に組み立てる設計である。利用者はまず対象を見つけ、次にその対象に対する操作を選ぶ。対象の一覧、詳細、編集を主軸にした画面構成になる。

例: 文書管理、プロジェクト管理、CRM、会計システム。ナビゲーションには「請求書」「顧客」「契約」といった対象の名前が並ぶ。

### タスク指向 UI

典型的な作業（動詞）を中心に組み立てる設計である。利用者は達成したい目的を選び、システムが段階的に手順を示す。ウィザード、ガイドつき入力、明示的な完了画面を主軸にした構成になる。

例: 税務申告サービス、保険請求、初回セットアップ。ナビゲーションには「申告する」「書類を提出する」「設定を完了する」といった作業の名前が並ぶ。

## 選択基準

どちらを採用するかは、ドメインの専門性と対象ユーザーの習熟度で決める。

### ドメインとユーザーによる判断

**必須**

- ドメインが専門的であり、対象ユーザーがそのドメインに習熟している場合は、オブジェクト指向 UI を採用する。専門家は対象と操作の関係をすでに知っているため、対象から操作を選ぶほうが速い。
- ドメインが日常的である場合は、オブジェクト指向 UI を採用する。利用者はドメインの対象を日常の知識から理解できる。
- ドメインが専門的であり、対象ユーザーがそのドメインに習熟していない場合は、タスク指向 UI を採用する。専門的な対象を前提知識なしに操作させるには、典型的な手順をシステムが示す必要がある。

例:

- 会計システム（専門的、経理担当者向け）→ オブジェクト指向。「仕訳」「勘定科目」といった対象を並べる。
- メモアプリ（日常的、一般向け）→ オブジェクト指向。「ノート」「フォルダ」といった対象を並べる。
- 医療費控除の申告サービス（専門的、一般消費者向け）→ タスク指向。「医療費を申告する」という作業を段階的に示す。

### ナビゲーションからの判断

**推奨**

- ドメインの対象をナビゲーションに並べたとき、利用者がその対象の名前から業務の流れを想像できるなら、オブジェクト指向 UI を採用する。
- ドメインの対象を並べても流れを想像しにくく、利用者が「次に何をすればよいか」を必要とするなら、タスク指向 UI を採用する。

この判断は、前項の基準を補足するものである。ドメインと利用者の組み合わせで迷う場合に、ナビゲーションの見え方を想定して確認する。

## 画面設計への影響

選択した方向性は、次の設計要素に具体的な影響を与える。

### ナビゲーション

- オブジェクト指向: 対象の名前（請求書、契約、顧客）を並べる。
- タスク指向: 作業の名前（申告する、提出する、確認する）を並べる。

### 主要画面

- オブジェクト指向: 対象の一覧、詳細、編集を主画面にする。操作は対象を選んだあとに出す。
- タスク指向: 作業の開始画面と段階的な入力を主画面にする。進捗と次の段を明示する。

### 空状態

- オブジェクト指向: 「対象がまだありません」と、対象を作成する操作を示す。
- タスク指向: 「作業を始めましょう」と、最初の段への案内を示す。

## 混在する画面

一つのプロダクトに両方の画面があるときは、画面ごとに方向性を選ぶ。プロダクト全体で統一する必要はない。

例: SaaS の管理画面（オブジェクト指向）と、そのサービス内の初回セットアップウィザード（タスク指向）が混在する。

この扱いは、[サービス別の特化ルール](./services/README.md) が画面ごとに文書を選ぶ方針と同じである。

## レビュー項目

方向性を選んだあと、次の点を確認する。

- [ ] ドメインの専門性と対象ユーザーの習熟度から、適切な方向性を選んだか
- [ ] ナビゲーションに並ぶ項目が、選んだ方向性と一致しているか（対象名か作業名か）
- [ ] 主要画面が、選んだ方向性の主軸（一覧・詳細・編集か、段階的な手順か）に沿っているか
- [ ] 空状態のメッセージが、方向性に合った案内（対象の作成か、作業の開始か）になっているか
